## Design Overview

Spigot is a **pay-per-call API gateway** that settles real TIP-20 transfers on the Tempo L2. One principle runs through it: **payment is the credential**. There are no API keys for the paid endpoints and no session cookies — a receipt that verifies against the chain is what unlocks a response.

### Design goals

1. **Sub-cent charges** — $0.005 for weather, $0.02 for premium data
2. **A price that cannot drift** — every surface reads `lib/pricing.ts`
3. **Verification that trusts the chain, not the client** — the receipt's own fields are treated as claims and re-derived
4. **One signer abstraction** — a local key or a Dynamic MPC wallet, chosen by env var
5. **Runnable without credentials** — the free routes, the docs and the CLI self-test all work with no keys

### What is deliberately not here

| Absent | Consequence |
|---|---|
| Database | Transactions, usage logs and revenue history are process memory and reset on restart |
| Shared replay store | Redeemed hashes live in a `Map`; a second instance would accept a receipt the first already spent |
| Rate limiting | Nothing caps request volume. `POST /api/pay` is unmetered |
| Webhooks | No outbound notification code exists |
| Redis / queue / cache | No external infrastructure is required or used |

`cli/tempo/` is a separate Node ESM walkthrough. It shares no code with `lib/tempo/`; it exercises Dynamic wallet creation, faucet funding and `mppx.fetch` against an external 402 endpoint.

`lib/data/` sits on the other side of the paywall — the actual data the paid endpoints sell. `weather.ts` wraps Open-Meteo (geocode, then current conditions) and `market.ts` wraps CoinGecko (prices plus global aggregates). `cache.ts` is a process-local TTL cache in front of both: it dedupes concurrent callers onto one upstream request, and it never caches a failure, so a transient upstream blip is not sticky. Weather is cached 15 minutes and its geocodes for 24 hours; the market snapshot for 60 seconds.

`app/demo` performs the handshake for real from the browser: it requests the endpoint with no receipt, checks it answers 402, calls `POST /api/pay`, redeems with the returned receipt, and then replays the same receipt to show it is refused. Each step's message comes from that step's actual response. It needs no LLM key.

## Data flow

### A paid request

```
Client                     Gateway                     Tempo
  │                          │                           │
  │ GET /api/weather         │                           │
  │─────────────────────────▶│                           │
  │                          │                           │
  │ 402 { price, howToPay }  │                           │
  │◀─────────────────────────│                           │
  │                          │                           │
  │ POST /api/pay            │                           │
  │ { amount, endpoint,      │                           │
  │   agentId }              │                           │
  │─────────────────────────▶│ settlePayment()           │
  │                          │ signs + broadcasts ──────▶│
  │                          │                           │
  │ 200 { receipt }          │◀────── txHash ────────────│
  │◀─────────────────────────│                           │
  │                          │                           │
  │ GET /api/weather         │                           │
  │ Payment-Receipt: …       │                           │
  │ X-Agent-Id: …            │                           │
  │─────────────────────────▶│ verifyReceipt()           │
  │                          │ eth_getTransactionReceipt ▶│
  │                          │ decode calldata ─────────▶│
  │                          │◀────── receipt ────────────│
  │ 200 { data, payment }    │                           │
  │◀─────────────────────────│                           │
```

### Verification order

`verifyReceipt` in `lib/tempo/payment.ts` runs these in sequence and stops at the first failure, so a cheap local check precedes an RPC read:

| # | Check | Rejects |
|---|---|---|
| 1 | Parses as base64url JSON | Anything not minted by `/api/pay` |
| 2 | Required fields present | A truncated or hand-rolled blob |
| 3 | `endpoint` equals the route being called | A receipt bought for a cheaper route |
| 4 | `agentId` matches `X-Agent-Id` when sent | Another agent spending this receipt |
| 5 | Transaction exists on Tempo | A fabricated hash |
| 6 | Receipt present (not pending) | A broadcast that has not landed |
| 7 | Status succeeded | A reverted transfer |
| 8 | Target is the token in the receipt | A receipt pointed at another contract |
| 9 | Calldata decodes as a TIP-20 `transfer` | The wrong call shape |
| 10 | Calldata recipient equals `TEMPO_MERCHANT_ADDRESS` | Payment settled to the payer's own wallet |
| 11 | Calldata amount ≥ the endpoint price | Underpayment |
| 12 | Calldata amount equals the receipt's `amount` | A receipt claiming more than moved |
| 13 | Hash not already redeemed | Replay |

Steps 9–12 read the transaction's calldata rather than the receipt's fields. That is the point: every field in the receipt is supplied by whoever presents it, so the amount and recipient are taken from what actually moved on chain. The recipient check is what makes this a paywall rather than a proof that somebody transferred some TIP-20s.

### The agent run

`lib/agent-graph.ts` is a LangGraph `StateGraph` over a `MemorySaver`, run single-shot:

```
START → decide ─┬─(no tool)→ END
                │
                ▼
               pay  ── settles via POST /api/pay
                ▼
               call ── verifyReceipt(markRedeemed:false)
                │      then GET the endpoint with the receipt
                ▼
             reflect ── error / done / step cap → END
```

Two details that were bugs and are worth preserving:

- **`markRedeemed: false`** on the agent's pre-flight verification. That check and the endpoint's own check both run on the same receipt; if the agent consumed the replay guard, the endpoint would reject its own payment as a replay and the run would report a failure after paying.
- **Arguments go out as a query string.** Tool args were being dropped, so the agent paid for `weather` and then called `/api/weather` with no `city`, receiving an arbitrary one.

`reflect` retains its loop edge for the `step >= MAX_STEPS` cap, but nothing routes back to `decide` in practice: the node sets `done`, and re-deciding had no real tool-chaining to justify a second payment.

### Funding

`POST /api/agent/fund` verifies an **inbound** transfer with `verifyInboundPayment`: the transaction must exist, be confirmed, decode as a TIP-20 transfer, and send at least the requested amount **to the agent's own address**. The credited figure is read from calldata, not from the request body. A browser cannot sign, so the flow is: send tokens to the address from `/api/agent/status`, then submit the resulting hash.

## Security model

### What holds

| Property | How |
|---|---|
| Forged receipts | Rejected — verification re-derives everything from chain state |
| Self-payment | `/api/pay` returns `400` for a `to` that is not the merchant address |
| Receipt laundering across routes | `endpoint` is bound into the receipt and checked |
| Replay within one process | Redeemed hashes are recorded and rejected |
| Credential leakage in status output | `/api/agent/status` reports `configured: boolean`, never key material |
| Merchant destination | Required explicitly; unset, invalid, zero, and known dead addresses block settlement |

### What does not hold

Stated plainly, because each is easy to assume from the docs elsewhere:

- **The receipt is not a signature.** It is unsigned base64url JSON.
- **Replay protection is per-process.** Two instances would each accept the other's receipts.
- **No rate limiting.** Replay stops double-spending one receipt; it does not cap how many receipts are minted.
- **`/api/pay` is unmetered.** It signs and broadcasts on every call.
- **No HTTPS enforcement or authn on paid routes.** A receipt is the only gate.
- **Merchant destination is required.** Settlements fail closed until you set a valid address you control.

### Key handling

With `TEMPO_SIGNER=privateKey` the private key lives in the process environment. Dynamic MPC configuration exists, but the app payment broadcaster currently requires the private-key signer; Dynamic signing does not yet broadcast app payments.

## Limits

| Limit | Detail |
|---|---|
| Single instance required | The replay `Map`, the store, the LangGraph `MemorySaver` and the upstream TTL cache are all in-process |
| A paid caller whose upstream fails has still paid | Both paid routes fetch upstream *after* the receipt verifies, because verifying first is what stops unpaid callers costing a third party a request. If Open-Meteo or CoinGecko then fails the response is 502 with the `payment` block attached — the charge cannot be reversed |
| Upstream cache is per-instance | A second instance refetches rather than sharing, which costs quota but is otherwise correct |
| Unbounded growth is capped, not solved | `MAX_TRANSACTIONS` 1000, `MAX_USAGE_LOGS` 2000, revenue history 30 days, cache 500 keys — older entries are dropped |
| Revenue resets on restart | No persistence |
| Agent memory is not wired end to end | `threadId` is accepted and returned, but `MemorySaver` checkpoints are never evicted or enumerated, so nothing reuses them |
| `getNativeBalance()` is meaningless here | It divides by 1e18 assuming an 18-decimal native unit, which Moderato does not have. No route surfaces it; `/api/agent/status` reports the TIP-20 balance instead |

Scaling past one instance requires moving the replay set, the store and the checkpointer to shared storage. Nothing in the verification logic needs to change — only the three places that assume process-local state.
