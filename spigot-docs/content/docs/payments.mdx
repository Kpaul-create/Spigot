## How the 402 Payment Flow Works

Paid endpoints answer `402 Payment Required` until a payment is attached. There is no API key — payment itself is the credential.

The handshake is **three HTTP calls, not two**. The payment is settled by a separate endpoint, and the resulting receipt is replayed against the paid endpoint. This is the single most important thing to understand, because the receipt is *not* the signed transaction and the server does not emit `Payment-Required` or `Payment-Info` headers.

### The protocol

```
┌──────────┐                                          ┌──────────┐
│  Client  │                                          │  Server  │
└────┬─────┘                                          └────┬─────┘
     │                                                     │
     │  1. GET /api/weather                                │
     │ ──────────────────────────────────────────────────▶ │
     │                                                     │
     │  2. 402 Payment Required                            │
     │     { error, message, price, howToPay }             │
     │ ◀────────────────────────────────────────────────── │
     │                                                     │
     │  3. POST /api/pay                                    │
     │     { amount, endpoint, agentId }                   │
     │ ──────────────────────────────────────────────────▶ │
     │                                                     │
    │     [Server signs with the configured signer        │
    │      and transfers to the merchant destination]     │
     │                                                     │
     │  4. 200 { receipt: "eyJjaGFpbklk…" }                │
     │ ◀────────────────────────────────────────────────── │
     │                                                     │
     │  5. GET /api/weather                                │
     │     Payment-Receipt: eyJjaGFpbklk…                  │
     │ ──────────────────────────────────────────────────▶ │
     │                                                     │
     │     [Server re-reads the transfer from Tempo and     │
     │      checks amount, recipient, endpoint and replay] │
     │                                                     │
     │  6. 200 { data: … }                                 │
     │ ◀────────────────────────────────────────────────── │
     │                                                     │
```

The server holds the configured signer wallet and sends the transfer to the merchant destination. The client never signs anything.

### Why 402?

HTTP status code `402 Payment Required` was reserved in the original HTTP/1.1 spec but never widely adopted. It is exactly what it was intended for: **the server requires payment before serving the request**.

## Payment Receipt Format

The receipt is **base64url-encoded JSON** — an assertion naming a transaction, not a signature:

```json
{
  "chainId": 42431,
  "txHash": "0x5d0f34…79b8",
  "blockNumber": "37862711",
  "from": "0x19E7E376…",
  "to": "0x1234567890abcdef1234567890abcdef12345678",
  "token": "0x20c0000000000000000000000000000000000000",
  "amount": "5000",
  "endpoint": "/api/weather",
  "agentId": "agt-0000"
}
```

Every field in it is supplied by whoever presents it, so **a receipt proves nothing on its own**. `verifyReceipt` re-derives the truth from Tempo and ignores the claims that can be forged. Amount and recipient are read out of the transaction's calldata, not from this blob — `amount: "5000"` here is only cross-checked against what actually moved.

The checks, all of which must pass:

| Check | Rejected because |
|---|---|
| Transaction exists on Tempo | Nothing found at that hash |
| Receipt reached on-chain | `blockNumber` is null — still pending |
| Transaction succeeded | The transfer reverted |
| Target is the token in the receipt | Called a different contract |
| Calldata decodes as a TIP-20 transfer | Wrong shape or wrong selector |
| Amount in calldata ≥ the endpoint price | Underpaid |
| Recipient in calldata is `TEMPO_MERCHANT_ADDRESS` | Paid someone else |
| `endpoint` matches the route being called | Receipt bought for a cheaper route |
| `agentId` matches `X-Agent-Id` when sent | Receipt bound to a different agent |
| Hash not already redeemed | Replay |

The recipient check is the one that makes this a paywall. Without it, a receipt only proved that *somebody* transferred *some* TIP-20 of the right amount — which the payer satisfies by settling to a wallet they control.

### Replay protection is per-process

Redeemed hashes are held in a `Map` in the server process, not in shared storage. A second instance would accept a receipt the first had already used. Fine for the single-instance deployment this is written for; it does not hold under horizontal scaling.

## Integration Examples

### Node.js

```javascript
const BASE = 'http://localhost:3000';

// 1. Discover the price. A 402 tells you what the endpoint costs.
const challenge = await fetch(`${BASE}/api/weather`);
if (challenge.status !== 402) throw new Error(`Expected 402, got ${challenge.status}`);

const { price } = await challenge.json();

// 2. Settle the payment. The server holds the wallet and broadcasts the transfer.
const payment = await fetch(`${BASE}/api/pay`, {
  method: 'POST',
  headers: { 'content-type': 'application/json' },
  body: JSON.stringify({
    amount: price,
    endpoint: '/api/weather',
    agentId: 'agt-0000',
  }),
});

if (!payment.ok) throw new Error(`Payment failed: ${await payment.text()}`);

const { receipt } = await payment.json();

// 3. Redeem it. `X-Agent-Id` is optional but binds the receipt to you, which
//    stops another agent from spending it.
const response = await fetch(`${BASE}/api/weather`, {
  headers: { 'Payment-Receipt': receipt, 'X-Agent-Id': 'agt-0000' },
});

const { data } = await response.json();
console.log(data);
```

### cURL

```bash
BASE=http://localhost:3000

# 1. Get the challenge — 402 with the price
curl -s "$BASE/api/weather"

# 2. Settle the payment
RECEIPT=$(curl -s -X POST "$BASE/api/pay" \
  -H "content-type: application/json" \
  -d '{"amount":0.005,"endpoint":"/api/weather","agentId":"agt-0000"}' \
  | jq -r .receipt)

# 3. Redeem
curl -s "$BASE/api/weather" \
  -H "Payment-Receipt: $RECEIPT" \
  -H "X-Agent-Id: agt-0000"
```

### Python

```python
import requests

BASE = 'http://localhost:3000'

challenge = requests.get(f'{BASE}/api/weather')
if challenge.status_code != 402:
    raise Exception(f'Expected 402, got {challenge.status_code}')

payment = requests.post(f'{BASE}/api/pay', json={
    'amount': challenge.json()['price'],
    'endpoint': '/api/weather',
    'agentId': 'agt-0000',
})
payment.raise_for_status()
receipt = payment.json()['receipt']

response = requests.get(f'{BASE}/api/weather', headers={
    'Payment-Receipt': receipt,
    'X-Agent-Id': 'agt-0000',
})

print(response.json()['data'])
```

## Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| `402 persists after sending a receipt` | No `Payment-Receipt` header on the retry | Send it; header name is exact |
| `Receipt is malformed or not a Spigot receipt` | Receipt did not come from `/api/pay`, or is not base64url JSON | Mint it via `/api/pay` |
| `Payment settled to 0x…, not the merchant address` | Transfer went elsewhere | Set `TEMPO_MERCHANT_ADDRESS` and pay without a `to` override |
| `Paid 0.001, need at least 0.005` | Underpaid | The price is the floor, not a suggestion |
| `Receipt has already been redeemed` | Replay | Pay again for a new receipt |
| `Transaction 0x… is not confirmed yet` | Still propagating | Retry in a few seconds |
| `Transaction 0x… reverted` | Transfer failed on-chain | Check the tx on the explorer |
| `Receipt is for /api/x, not /api/y` | Receipt was minted for a different route | `endpoint` is bound into the receipt |
| `Receipt belongs to agent X, not Y` | `X-Agent-Id` disagrees with the receipt | Send a matching `X-Agent-Id`, or omit the header |
| `Wallet not configured` (503 from `/api/pay`) | No supported signer | Set `TEMPO_PRIVATE_KEY`; Dynamic broadcasting is not supported by the app yet |
| `Merchant destination unavailable` (503) | Merchant address is missing, invalid, or a known burn address | Set `TEMPO_MERCHANT_ADDRESS` to a wallet you control |
| `Invalid settlement address` (400) | `to` is not the merchant | Omit `to`; the server uses `TEMPO_MERCHANT_ADDRESS` |

### Debugging

Check what the chain actually holds:

```bash
curl -X POST https://rpc.moderato.tempo.xyz \
  -H "content-type: application/json" \
  -d '{"jsonrpc":"2.0","id":1,"method":"eth_getTransactionReceipt","params":["0x…"]}'
```

Confirm the wallet is funded and the signer is wired up:

```bash
curl -s http://localhost:3000/api/agent/status
```

`wallet.configured: false` means `/api/pay` will refuse; `model.configured: false` means `LLM_GATEWAY_API_KEY` is unset, which only affects the agent routes.

### Common mistakes

1. **Treating the receipt as a signature.** It is unsigned JSON. Presenting a receipt grants nothing until the transaction behind it is re-read from Tempo.
2. **Settling to your own wallet.** `/api/pay` now rejects a `to` that is not the merchant address, because a receipt backed by a transfer to the payer is worthless — and used to be redeemable.
3. **Omitting `endpoint` when paying.** It defaults to `/api/pay`, and a receipt is bound to the route it was bought for.
4. **Sending `X-Agent-Id` inconsistently.** If you send it, the receipt's `agentId` must match.
5. **Verifying a receipt yourself by re-sending it.** Verification consumes it; a second attempt returns `402`.
